# Централизованное развёртывание и обновление (для ИТ / техподдержки)

Документ для системных администраторов. Описывает, как установить и обновлять
Voice Input Local централизованно, без действий со стороны пользователей, и как
отключить встроенную проверку обновлений, когда обновлениями управляет ИТ
(например через **Kaspersky Security Center** или групповые политики).

Обычному пользователю ничего настраивать не нужно — всё делает администратор
один раз на уровне задачи развёртывания.

---

## 1. Тихая (silent) установка и обновление

Установщик собран на Inno Setup и понимает стандартные ключи «тихой» установки.
Обновление ставится тем же установщиком **поверх** предыдущей версии.

Команда для тихой установки/обновления:

```
VoiceInputLocalSetup-X.Y.Z.exe /VERYSILENT /NORESTART /SUPPRESSMSGBOXES
```

Что означают ключи:

| Ключ | Значение |
|---|---|
| `/VERYSILENT` | Установка без окон мастера и без окна прогресса. |
| `/SILENT` | То же, но показывается небольшое окно прогресса (альтернатива `/VERYSILENT`). |
| `/NORESTART` | Не перезагружать компьютер автоматически. |
| `/SUPPRESSMSGBOXES` | Не показывать всплывающие сообщения (ответы по умолчанию). |
| `/LOG="путь\файл.log"` | Записать подробный журнал установки в указанный файл (рекомендуется, см. ниже). |

### Журнал установки (`/LOG`)

Ключ `/LOG` — стандартная возможность Inno Setup: установщик пишет подробный
журнал всего процесса (распаковка файлов, ключи реестра, результат логики
обновления при открытом приложении из раздела 4 и код возврата). При тихой
централизованной установке это **единственный способ понять причину**, если
обновление не встало — окон мастера админ не видит.

Рекомендуемая форма — фиксированный путь, чтобы лог всегда лежал в одном месте:

```
/LOG="C:\ProgramData\VoiceInputLocal\install.log"
```

- Папка `C:\ProgramData\VoiceInputLocal` уже используется приложением (там лежат
  `busy.lock` и маркеры обновления), установщик создаёт её сам — путь доступен
  для записи.
- Кавычки обязательны, только если в пути есть пробелы; в этом пути их нет, но с
  кавычками надёжнее.
- Файл **перезаписывается** при каждой установке. Если нужно сохранять историю,
  указывайте путь с уникальным именем или собирайте логи с машин задачей KSC.
- Форма без пути (`/LOG` без `=`) пишет журнал во временный файл со случайным
  именем в `%TEMP%` — для централизованного развёртывания менее удобно.
- Ключ **никак не влияет** на поведение установки — только добавляет
  диагностический файл.

Особенности:

- **Установка машинная** — приложение ставится в `Program Files` и доступно всем
  учётным записям компьютера.
- **UAC не появляется**, если установщик запущен от имени системы (SYSTEM) —
  именно так его запускает Kaspersky Security Center. Ручной запуск из-под
  обычного пользователя по-прежнему потребует подтверждения UAC.
- **Обновление поверх** — переустановка новой версии в ту же папку сохраняет
  настройки пользователя (они лежат в профиле, см. README) и запись автозагрузки.

Коды возврата (стандартные для Inno Setup) — по ним система развёртывания
определяет результат:

| Код | Значение |
|---|---|
| `0` | Успех. |
| `1` | Не удалось запустить установку (внутренняя ошибка). |
| `2` | Пользователь отменил до начала установки. |
| `3`–`4` | Фатальная ошибка при инициализации / установке. |
| `5` | Пользователь отменил в процессе установки. |
| `6` | Установка прервана скриптом установщика. |
| `101` | **Отложено**: приложение занято активной работой — обновление не установлено (US-057). |

> Код `101` относится к обновлению во время активной работы (раздел 4): для KSC это
> «не установлено, повторить задачу позже».

## 2. Раздача через Kaspersky Security Center

1. Скачать `VoiceInputLocalSetup-X.Y.Z.exe` из релизов.
2. В консоли Kaspersky Security Center создать **инсталляционный пакет** из этого
   `.exe`.
3. В параметрах установки пакета указать ключи:
   `/VERYSILENT /NORESTART /SUPPRESSMSGBOXES /LOG="C:\ProgramData\VoiceInputLocal\install.log"`.
   Ключ `/LOG` необязателен, но настоятельно рекомендуется — без журнала при
   тихой установке невозможно диагностировать сбой обновления (см. раздел 1).
4. Создать **задачу удалённой установки** и назначить её на нужную группу
   компьютеров. Согласование выполняется один раз — на уровне задачи.
5. KSC раздаёт и запускает установщик от имени SYSTEM: приложение обновляется
   тихо, без окон и без UAC у пользователей.

Аналогично можно раздавать пакет через GPO (Software Installation) или другие
системы развёртывания (SCCM и т. п.).

## 3. Отключение встроенной проверки обновлений (машинная политика)

У приложения есть встроенная проверка обновлений с GitHub (всплывающее окно
«Обновление доступно»). Когда обновлениями управляет ИТ централизованно, эту
встроенную проверку следует отключить, чтобы она не беспокоила пользователей.

Отключение задаётся **машинной политикой в реестре**:

```
Раздел:   HKEY_LOCAL_MACHINE\SOFTWARE\Policies\VoiceInputLocal
Значение: DisableUpdates  (тип DWORD)
Данные:   1  — встроенные обновления отключены
          0 или отсутствует — обычное поведение
```

Готовый `.reg`-файл для отключения:

```reg
Windows Registry Editor Version 5.00

[HKEY_LOCAL_MACHINE\SOFTWARE\Policies\VoiceInputLocal]
"DisableUpdates"=dword:00000001
```

Что происходит при активной политике:

- приложение **не обращается к GitHub** и **не показывает** окно об обновлении
  ни одному пользователю;
- в настройках приложения (раздел обновлений) поля и кнопка «Проверить
  обновления» заблокированы, показана пометка
  «Обновлениями управляет системный администратор»;
- политика имеет **приоритет** над пользовательской галочкой «Проверять
  обновления автоматически» — пользователь не может её обойти (ветка `Policies`
  недоступна ему на запись).

Раздать эту политику удобно через:

- **GPO** → Group Policy Preferences → Registry (создать значение в
  `HKLM\SOFTWARE\Policies\VoiceInputLocal`), или
- **Kaspersky Security Center** (задача изменения реестра), или
- вручную применив `.reg` от имени администратора.

**Как временно вернуть** самостоятельное обновление (например, для точечного
тестирования нового релиза): установить `DisableUpdates` в `0` или удалить
значение/раздел. После этого пользователь снова сможет обновляться сам кнопкой
в приложении. На машинах, где политика не применялась, самостоятельное
обновление доступно по умолчанию.

## 4. Обновление при открытом приложении: активная работа и простой (US-057, US-058)

Централизованное обновление не прерывает идущую работу (например, расшифровку
часовой встречи) и не требует, чтобы пользователь заранее закрывал программу:

- если приложение **занято** — пользователь сам решает, обновиться сейчас или
  продолжить работу (US-057);
- если приложение **открыто, но простаивает** — обновление ставится тихо;
  приложение закрывается само и **возвращается штатным автозапуском Windows**
  при следующем входе/перезагрузке (US-058/US-061). Пользователю ничего делать
  не нужно.

Как это работает:

- Пока приложение занято (запись, диктовка, расшифровка файла, суммаризация),
  оно держит маркер `busy.lock` в папке `%ProgramData%\VoiceInputLocal`.
- Тихий установщик перед заменой файлов проверяет маркер:
  - **Приложение простаивает** (US-058):
    - если приложение **закрыто** → обновление ставится сразу, тихо (код `0`);
    - если приложение **открыто и простаивает** → установщик не полагается на
      принудительное закрытие (из-под SYSTEM закрыть окно пользователя нельзя),
      а сигналит приложению и в том же запуске ждёт его закрытия. Приложение
      показывает сообщение **«Устанавливается обновление, приложение закроется…»**,
      закрывается само, обновление ставится (код `0`). Программа **возвращается
      штатным автозапуском Windows** при следующем входе/перезагрузке (US-061).
      Если приложение не закрылось за отведённое время → установщик откладывает
      (код `101`), задача повторяется позже.
  - **Приложение занято** → установщик сигналит приложению показать окно
    **«Закрыть и обновить / Отклонить»** и ЖДЁТ решения в том же прогоне (до
    нескольких минут). **ВАЖНО:** таймаут задачи KSC должен быть больше этого
    ожидания, иначе задача упадёт по времени.
- Выбор пользователя (обрабатывается приложением, US-059):
  - **«Закрыть и обновить»** → приложение показывает «Устанавливается
    обновление…», закрывается, установщик тут же ставит обновление (код `0`).
    Программа возвращается автозапуском Windows при следующем входе.
  - **«Отклонить»** → приложение сигналит установщику, тот сразу прекращает
    ожидание и завершается кодом `101` («Отложено»); пользователь продолжает
    работу, окно появится снова при следующей занятой попытке KSC.

> **Таймаут задачи в KSC (US-059).** На «занятом» пути установщик ждёт решения
> пользователя до нескольких минут (по умолчанию 3). Убедитесь, что таймаут
> задачи развёртывания в KSC больше этого значения, иначе KSC прервёт установщик
> во время ожидания.
- Устаревший маркер после аварийного завершения снимается самим приложением
  при следующем запуске, поэтому обновление не блокируется навсегда.

> **Возврат приложения после обновления (US-061).** Приложение при обновлении
> НЕ запускает никаких процессов (прежний авто-перезапуск через фоновый
> PowerShell блокировался поведенческим антивирусом как подозрительный). Оно
> возвращается **штатным автозапуском Windows** при следующем входе/перезагрузке —
> убедитесь, что у пользователя включён «Запуск вместе с Windows». Для
> **немедленного** открытия без ожидания входа можно настроить в KSC отдельную
> задачу **«Запуск процесса»** (`VoiceInputLocal.exe`) после задачи обновления —
> предварительно проверьте, открывает ли она окно в сессии пользователя (агент
> KSC работает под SYSTEM и может стартовать процесс в невидимой сессии 0).

> **Важно про первое обновление на US-058.** Механизм тихого самозакрытия и
> авто-перезапуска при простое работает начиная с версии, где он появился
> (4.17.4). Если обновляется **уже запущенная** более старая версия, она этот
> сигнал не понимает: такое обновление откладывается (код `101`), пока приложение
> не будет закрыто (пользователь закроет сам, или установится при следующем
> простое с закрытым приложением). Начиная с 4.17.4 открытое простаивающее
> приложение обновляется само.

Установщик работает под SYSTEM без интерфейса и сам окно показать не может — его
показывает работающее приложение; установщик лишь сигналит через файл-маркер и
сразу выходит. Поэтому при занятости результат для KSC всегда один — `101`
(«Отложено»), а не «установлено»; когда пользователь освободится/примет —
очередная попытка задачи ставит обновление (код `0`). Задача развёртывания
должна **повторяться**.

**Что настроить в KSC (по задаче):** включите повтор / запуск пропущенных
(например, каждые 30–60 минут). Трактовка кодов возврата:

| Код | Что значит | Действие KSC |
|---|---|---|
| `0` | Обновление установлено | успех |
| `101` | Приложение занято — отложено | повторить задачу позже |
| прочие ненулевые | Ошибка установки Inno | как ошибку |

### ⚠️ Обязательно: заставить KSC читать код возврата

По умолчанию KSC **не анализирует код возврата** исполняемого файла: он
дожидается завершения процесса и рапортует «Завершена успешно» **независимо от
кода**. Поэтому без настройки код `101` (и даже реальные ошибки установки)
отображаются как успех, а отложенное обновление считается установленным и не
повторяется.

Чтобы KSC учитывал коды, нужно **три** вещи:

1. **Отредактировать файл пакета** `.kpd` (кодировка **ASCII/ANSI**) или `.kud`
   (кодировка **Unicode** — обязательна для кириллических описаний). Кириллица в
   `.kpd`, сохранённом как UTF-8, ломает разбор — используйте `.kud` либо
   ASCII-описания в `.kpd`. Добавьте секции:

   ```
   [SetupProcessResult]
   Wait=1

   [SetupProcessResult_SuccessCodes]
   0=Installed

   [SetupProcessResult_ErrorCodes]
   101=Deferred - app busy
   ```
   (Любой код, не указанный в SuccessCodes, трактуется как ошибка.)

2. **Отредактировать пакет ДО создания задачи.** KSC фиксирует настройки пакета
   в момент **создания задачи**. Если правите `.kpd` у уже существующей задачи —
   **удалите задачу и создайте заново** (перезапуск существующей не перечитывает
   `.kpd`). При необходимости пересоздайте и сам пакет, чтобы Агент на устройстве
   не использовал кэш.

3. **Проверять при ЗАНЯТОМ приложении.** Если во время прогона приложение
   простаивало — установщик отдаёт `0` (установлено), и «успешно» это верно. Код
   `101` виден только когда идёт активная работа.

После этого: `0` → «Завершена успешно»; `101` и любой другой ненулевой код →
«ошибка» с понятным текстом → задача повторяется. Без этих секций код возврата
игнорируется.

> Замена US-048: раньше при занятости обновление откладывалось **молча** до
> простоя. Теперь при занятости пользователь сам выбирает «Закрыть и обновить /
> Отклонить»; результат для KSC при занятости всегда «Отложено» (`101`).
> Инфраструктура маркера `busy.lock` переиспользуется.

## 5. Что приложение читает с клавиатуры (для службы информационной безопасности)

Раздел отвечает на вопрос, который задают перед установкой: не является ли
программа для голосового ввода перехватчиком клавиатуры. Ниже — что именно
читается, в какие моменты и каким механизмом Windows.

### Чего приложение не делает

- **Не устанавливает низкоуровневый клавиатурный хук.** Вызовов
  `SetWindowsHookEx` с `WH_KEYBOARD_LL` в коде нет.
- **Не регистрирует сырой клавиатурный ввод** (`RegisterRawInputDevices`).
- **Не читает состояние всей клавиатуры разом** (`GetKeyboardState`) и не
  переводит нажатия в символы (`ToUnicodeEx`).
- **Не поглощает нажатия.** Ни одна клавиша, включая Escape, не перехватывается
  у активной программы: то же нажатие доходит до неё как обычно.
- **Не содержит библиотек, которые ставят хук.** Пакеты `keyboard` и
  `pyautogui` удалены из кода, зависимостей и сборки (версия 4.20.0).

До версии 4.20.0 приложение использовало библиотеку `keyboard`, а она ставила
низкоуровневый хук и получала все нажатия в системе. Это устранено.

### Что читается и когда

| Момент | Что читается | Механизм Windows |
|---|---|---|
| Приложение запущено, диктовка не идёт | **ничего** | — |
| Нажата горячая клавиша | факт срабатывания **только заданной пользователем комбинации** | `RegisterHotKey` → сообщение `WM_HOTKEY` |
| Идёт запись и распознавание | состояние **одной клавиши Escape** (для отмены) | `GetAsyncKeyState`, опрос 40 мс |
| Идёт запись в режиме Push-to-Talk | дополнительно состояние **тех 2–4 клавиш, из которых состоит комбинация пользователя** (чтобы поймать отпускание) | `GetAsyncKeyState`, опрос 40 мс |
| Идёт запись | состояние **сессии** — заблокирован ли экран (это не клавиатура) | `WTSQuerySessionInformation`, опрос 1 с |
| Непосредственно перед вставкой текста | однократная проверка, не удерживаются ли **Shift, Ctrl, Alt, Win, V** — иначе Ctrl+V превратился бы в другую команду | `GetAsyncKeyState` |
| Вставка текста | приложение **отправляет** Ctrl+V, а не читает ввод | `SendInput` |

Ключевые следствия:

- В режиме «Переключатель» состояние клавиш комбинации не опрашивается **вовсе**
  — только факт срабатывания от Windows.
- Наблюдение живёт ровно столько, сколько длится операция: включается при старте
  записи и гаснет при завершении, отмене, ошибке и при выходе из приложения.
- Набор опрашиваемых кодов **вычисляется из настроек самого пользователя**
  (его комбинация + Escape), а не задан произвольным списком в коде.
- Содержимое ввода не восстанавливается: читается только состояние
  «нажата/не нажата» перечисленных выше клавиш.

### Как это проверить

- Исходный код: `voice_input_app/hotkeys.py` (регистрация комбинации),
  `voice_input_app/key_watch.py` (единственное место чтения состояния клавиш),
  `voice_input_app/insert.py` (отправка Ctrl+V и проверка перед вставкой).
- Автоматическая проверка: `tests/test_us068_no_keyboard_capture.py` — падает,
  если в коде появится хук, регистрация сырого ввода, чтение клавиатуры вне
  перечисленных мест или библиотеки `keyboard`/`pyautogui`. Запуск:
  `.venv\Scripts\python.exe tests\test_us068_no_keyboard_capture.py`.
- Наблюдение со стороны: пока диктовка не идёт, у процесса нет активных
  клавиатурных хуков; это видно, например, в Process Explorer или через
  инструменты вашего решения по контролю рабочих станций.

## 6. Фильтр моделей Cloud.ru (для службы информационной безопасности)

Раздел отвечает на вопрос, который задают вместе с вопросом про клавиатуру:
может ли сотрудник выбрать облачную модель, при работе с которой расшифровка
уйдёт за пределы инфраструктуры Cloud.ru. Ниже — на чём основан отбор, где он
включается и как убедиться, что он действительно работает.

### Какую задачу решает

Один и тот же адрес Cloud.ru отдаёт и модели, развёрнутые внутри защищённого
контура, и модели внешних поставщиков, доступные через тот же шлюз. Для
персональных данных (152-ФЗ) это принципиально разные вещи, а на экране выбора
модели они выглядят одинаково. Пока фильтр включён, сотрудник не может выбрать
внешнюю модель: её нет ни в одном списке программы.

### На чём основан признак

Размещение сообщает **сам сервис**, программа его не угадывает. В ответе
`GET /v1/models` у каждой модели есть поле `metadata.provider`:

- `cloud.ru` — модель развёрнута в контуре Cloud.ru (внутренняя);
- `external` — модель внешнего поставщика (внешняя).

**По имени модели отличить нельзя** — это проверяемый факт, а не осторожность:
`openai/gpt-oss-120b` внутренняя, а `openai/gpt-oss-20b` внешняя. Адрес тоже не
признак: у всех моделей один и тот же хост, различает их только `metadata`.
Поэтому правило вида «раз в имени есть whisper — значит модель своя» заведомо
неверно, и в программе его нет.

Получить тот же список самостоятельно (PowerShell; ключ вводится в консоли и в
скрипты или документы не переносится, адрес — тот же, что указан в карточке
подключения):

```powershell
$key = Read-Host "API-ключ подключения"
$headers = @{ Authorization = "Bearer $key" }
$url = "https://foundation-models.api.cloud.ru/v1/models"
$r = Invoke-RestMethod -Uri $url -Headers $headers

# сводка: сколько моделей внутренних, сколько внешних
$r.data | Group-Object { $_.metadata.provider } | Select-Object Name, Count

# и поимённо, вместе с типом модели
$r.data |
    Select-Object id,
        @{ n = "provider"; e = { $_.metadata.provider } },
        @{ n = "type";     e = { $_.metadata.type } } |
    Sort-Object provider, id | Format-Table -AutoSize
```

То же поле `metadata.type` (`audio-to-text`, `llm`, `embedder` и т. п.)
программа использует, чтобы в списке моделей диктовки показывать только те
модели, которые распознают речь.

### Где включается

Флажок **«Показывать только модели, размещённые в Cloud.ru»** находится в
карточке подключения: вкладка **«Модели» → «Облачные модели»**, кнопка
**«Редактировать»**.

- Флажок задаётся **отдельно для каждого подключения**.
- По умолчанию он **включён** — в том числе для подключений, заведённых до
  обновления программы.
- Из рабочих окон (диктовка, файлы, плавающая плашка) фильтр снять нельзя:
  только правкой карточки подключения.
- Пометка «Внутренний безопасный эндпоинт Cloud.ru», которая заменяет
  предупреждение о передаче данных на подтверждение «безопасно», действует
  теперь **только при включённом фильтре**. Флажок снят — вернулось обычное
  предупреждение о передаче данных провайдеру.

Состояние видно прямо в таблице подключений, например:
`Ключ задан · моделей: N · скрыто фильтром Cloud.ru: M · только Cloud.ru`
(N и M — фактические числа вашего подключения).

### Почему это нельзя обойти

Отбор стоит **единственной точкой регистрации облачной модели** внутри
программы (`ModelManager._register_cloud_model`). Все списки выбора берут модели
из одного реестра, который наполняет только эта точка:

- модель диктовки;
- модель расшифровки файлов;
- модель улучшения расшифровки (постобработка);
- модель суммаризации;
- быстрый выбор модели правым нажатием по плавающей плашке.

Поэтому внешняя модель не может появиться ни в одном из них — независимо от
того, каким путём программа узнала о моделях: восстановление настроек при
запуске, проверка соединения администратором, фоновая проверка через полторы
секунды после старта. Запрет на регистрацию в обход этой точки закреплён
автоматической проверкой, которая падает при появлении второго пути.

Поведение **fail-closed**: если подключение, к которому относится модель, не
определяется (например, повреждена запись в `config.json`), модель **не
регистрируется вовсе**. Без подключения неизвестны ни размещение модели, ни
состояние флажка, а молча показать внешнюю модель хуже, чем не показать
никакую. В журнал в этот момент пишется предупреждение (см. ниже).

### Что происходит в пограничных случаях

| Ситуация | Поведение программы |
|---|---|
| Сервис перестал сообщать `metadata.provider` | Список **не расширяется**: ранее известные внутренние модели остаются, новые и неопознанные скрываются. При проверке соединения выводится предупреждение «Сервис больше не сообщает размещение моделей». |
| Подключение размещение не сообщает вовсе (сторонний OpenAI-совместимый сервис, ElevenLabs) | Флажок **недоступен**, рядом пояснение почему. Отбор не применяется, список моделей прежний, обычное предупреждение о передаче данных провайдеру продолжает работать. |
| Ранее выбранная модель попала под фильтр | Выбор не подменяется молча: модель помечена в списке как «(скрыта фильтром подключения)», а запуск диктовки или расшифровки файла останавливается окном с кнопкой «Открыть настройки». Продолжить «всё равно» нельзя. |
| Скрытая модель указана для постобработки или облачной суммаризации | Текст расшифровки ей **не отправляется**: постобработка пропускается и показывается исходный текст, для суммаризации предлагается локальная модель. |
| Подключение не определяется | Модели не регистрируются (fail-closed), облачные списки пусты. |

### Как проверить по журналу

Журнал: `%LOCALAPPDATA%\VoiceInputLocal\logs\app.log`. Искать строки
`US-073 registry:` (что попало в списки и что отсеяно) и `placement:` (что
ответил сервис). Реальные строки:

```
2026-08-19 10:20:52,753 | INFO | voice_input.models | US-073 registry: connection 'Cloud.ru' (conn-8bbfe9adb58e) — available 1, hidden by Cloud.ru filter 2 (external 2, placement unknown 0), skipped as non-STT 2, rejected without connection 0
2026-08-19 10:20:52,783 | INFO | voice_input.cloud_placement | placement: https://foundation-models.api.cloud.ru/v1 — моделей 5, с признаком размещения 5 (внутренних 3, внешних 2), с типом 5
```

Как читать первую строку: по подключению «Cloud.ru» в списки допущена 1 модель,
2 модели скрыты фильтром (обе с признаком `external`, моделей с неизвестным
размещением нет), ещё 2 не попали в список диктовки, потому что не распознают
речь, и ни одна модель не была отвергнута из-за неопределённого подключения.

Срабатывание fail-closed выглядит так (уровень `WARNING`):

```
2026-08-19 10:20:52,763 | WARNING | voice_input.models | US-073 registry: connection conn-1 not resolved (cfg loaded: False) — model 'openai/whisper-large-v3' NOT registered (fail-closed: placement and filter state unknown)
2026-08-19 10:20:52,764 | WARNING | voice_input.models | US-073 registry: connection conn-1 NOT FOUND in config — available 0, rejected without connection 5 (fail-closed)
```

### Как это проверить в коде

- `voice_input_app/cloud_placement.py` — разбор ответа `/v1/models` и решение
  «показывать ли модель». Модуль не обращается к сети и не зависит от
  интерфейса, поэтому его легко прочитать целиком.
- `voice_input_app/models.py` → `ModelManager._register_cloud_model` —
  единственная точка регистрации облачной модели, оба отбора стоят в ней.
- Автоматическая проверка: `tests/test_us073_cloudru_filter.py` — 23 проверки на
  фикстуре реального ответа сервиса, включая случай «внешняя модель с именем,
  похожим на модель распознавания речи», пропажу признака, поведение fail-closed
  и запрет регистрации в обход единственной точки. Запуск:
  `.venv\Scripts\python.exe tests\test_us073_cloudru_filter.py`.
- Наблюдение со стороны: при включённом фильтре в списках выбора модели внешних
  моделей нет; снятие флажка в карточке подключения возвращает их сразу, без
  повторной проверки соединения.

## 7. Заметки

- **Автозагрузка (запуск вместе с Windows)** включается самим пользователем в
  настройках приложения и хранится в его профиле. Централизованная установка её
  не включает и обновление её не сбрасывает.
- **Самостоятельное обновление пользователем** остаётся доступным на всех
  машинах, где политика из раздела 3 не применена. Централизованное управление —
  это опция, включаемая администратором по каждому компьютеру, а не жёсткое
  ограничение в программе.
